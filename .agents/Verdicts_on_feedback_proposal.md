## Opinions & Technical Evaluation of a Reviewer's Points

| Reviewer Issue| Relevance to CS6350 TPA-2 | Verdict on Reviewer's Proposal & How We Should Handle It |
| --- | --- | --- |
| **ETH3D foreground masks**<br> | **High.** The problem statement specifically asks for accuracy on a **foreground object**. A simple median disparity threshold includes the ground plane/walls near the camera, not just objects.| Agree. Moreover, on evaluation day you will receive an **unknown dataset** without ground-truth disparity or object masks. We should use a lightweight pre-trained segmentation model (e.g., `torchvision` Mask R-CNN / DeepLabV3 or `ultralytics` YOLOv8-seg) to automatically generate consistent semantic foreground masks for ETH3D *and* the evaluation-day dataset, while keeping `disp > median` only as a clearly labeled `geometric_proxy` fallback.|
| **Ground-truth availability**<br> | **Critical.** In both KITTI 2015 and ETH3D, official `test` splits withhold ground truth for public leaderboard submission.| Agree. Your agents must split the **official `training` sets** (200 labeled pairs in KITTI 2015; 27 labeled pairs in ETH3D) into a small tuning split (e.g., 20%) and an evaluation split (80%) for quantitative metrics, and use the `test` split strictly for qualitative visual comparisons.|
| **KITTI disparity decoding**<br> | **Critical.** OpenCV's `StereoBM` outputs disparity scaled by `16.0`, whereas KITTI's 16-bit PNG ground truth is scaled by `256.0` (with `0` = invalid). Mixing these up ruins every metric.| Agree. Explicitly enforce `gt_disp = uint16_png.astype(np.float32) / 256.0` and `valid_mask = (uint16_png > 0)` in the Stage 1 specification.|
| **Metric depth ($Z = fB/d$)**<br> | **High.** Calibration files differ per scene/camera (`calib_cam_to_cam` in KITTI vs `calib.txt` in ETH3D). Also, on evaluation day, your unknown dataset might not include a calibration file!| Agree. Standardize $f$ in pixels and $B$ in meters ($Z$ in meters). Additionally, build a graceful fallback: if calibration is missing on evaluation day, output relative depth ($1/d$) and normalized disparity maps so the pipeline never crashes.|
| **Fair comparison (Valid-pixel policy)**<br> | **Critical.** Shallow methods (`BM`/`SGBM`) leave "holes" (invalid pixels with `disp <= 0`) in textureless areas, whereas deep networks predict dense values everywhere.| Agree. If you only evaluate where a shallow method is valid, `BM` looks artificially accurate because its hardest pixels are skipped. We must record **Density (%)** alongside **Fair Full-GT Evaluation** (evaluating all methods on all valid GT pixels).|
| **Model compatibility & Runtime**<br> | **High.** GPU initialization and CUDA kernel compilation on the first frame take 2–5 seconds, which will skew average FPS on small datasets like ETH3D.| Agree. Perform 3 warm-up iterations and use `torch.cuda.synchronize()` before starting the `time.perf_counter()` timer.|
| **Disparity vs. Metric Depth Error**<br> | **Critical Insight.** Because $Z = fB/d$, error grows quadratically with distance ($\Delta Z \approx \frac{Z^2}{fB} \Delta d$). Background sky/road pixels at $80\text{ m}$ completely dominate RMSE, hiding foreground performance.| Agree. Report Disparity metrics (`EPE`, `D1-all`, `D1-fg`) and Metric Depth metrics (`RMSE`, `AbsRel`) in clearly separated table columns, capping metric depth evaluation at standard ranges (e.g., $0.5\text{ m} \le Z \le 80\text{ m}$ for KITTI).|
